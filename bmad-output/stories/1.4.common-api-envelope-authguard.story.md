# 1.4: 공통 API 응답 엔벨로프 및 인증 가드

**Story ID:** 1.4
**Epic:** 1 — Foundation & Project Setup

**Branch:** `feature/1.4-common-api-envelope-authguard` (base: `feature/nextjs-migration`)

## Story

As a **개발자(본인)**,
I want **모든 API가 공유할 공통 응답 엔벨로프 헬퍼와 인증 가드 유틸을 만들어 두**,
so that **Epic 2~5의 모든 Route Handler가 일관된 응답 형식과 인증 체크를 재사용할 수 있다**.

## Acceptance Criteria

1. `lib/api/response.ts`에 성공/실패 응답 헬퍼(`ok(data)`, `fail(code, message, status)`)가
   있고, `{ success: true, data, message: "OK" }` / `{ success: false, message, code }` 형식을
   따른다.
2. `lib/api/error-codes.ts`에 기존 에러 코드(`INVALID_REQUEST`, `UNAUTHORIZED`, `FORBIDDEN`,
   `NOT_FOUND`, `DUPLICATE_REQUEST`, `GITHUB_API_ERROR`, `AI_API_ERROR`, `INTERNAL_ERROR`)가
   상수로 정의되어 있고 각각 올바른 HTTP 상태 코드(400/401/403/404/409/502/502/500)에
   매핑된다.
3. `lib/domain/auth/require-user.ts`에 인증 가드 헬퍼가 있어, 세션이 없으면 401 UNAUTHORIZED
   엔벨로프를 반환하고, 있으면 현재 `userId`를 반환한다.
4. `GET /api/health` Route Handler가 위 유틸을 사용해 정상 동작하는 예시로 존재한다.

## Dev Notes

- 응답 엔벨로프 형식과 에러 코드 표는 ADR-005를 그대로 따른다 (LOCKED 규약 — 이후 스토리는
  임의의 새 응답 형태를 만들지 않는다). [Source: architecture.md#adr-005-rest--json-응답-엔벨로프-규약]
- 기존 `RATE_LIMIT_EXCEEDED`(429) 코드는 PRD에서 rate limiting이 Out of Scope로 확정되어
  이번 에러 코드 목록에서 제외한다. [Source: prd.md#out-of-scope]
- 인증 가드는 1.3에서 구성한 Auth.js `auth()` 헬퍼를 감싸는 얇은 wrapper로 구현한다.
  [Source: architecture.md#adr-003-github-oauth-via-authjs-jwt-세션]
- 인가(authorization) 규칙은 "본인 소유 리소스만 접근 가능"이며 각 API에서 리소스의 `userId`가
  현재 세션의 `userId`와 일치하는지 검증하는 방식이다 (별도 RBAC 불필요, 1인 전용 서비스).
  [Source: architecture.md#nfr-002--security--encryption-at-rest-authentication]
- 이후 Epic 2~5의 모든 API Route Handler는 이 스토리의 `ok()`/`fail()`/`requireUser()`를
  재사용해야 한다 — 새 헬퍼를 중복 작성하지 않는다. [Inference]

## Testing

- **Approach:** 단위 테스트(응답 헬퍼, 에러 코드 매핑, 인증 가드) + 헬스체크 라우트 수동 호출.
- **Key scenarios:** 성공 응답 형태 검증, 실패 응답 형태 검증, 미인증 요청 시 401 반환, 인증된
  요청 시 `userId` 정상 반환.
- **Per-AC verification:** AC#1 → 단위 테스트로 `ok()`/`fail()` 출력 JSON 형태 검증; AC#2 → 각
  에러 코드별 상태 코드 매핑 단위 테스트; AC#3 → 세션 없음/있음 두 케이스에 대한 단위 테스트
  (mock `auth()`); AC#4 → `curl /api/health` 수동 호출로 200 + 엔벨로프 형식 확인.
- **Fixtures / mocks:** Auth.js `auth()` 세션 mock(로그인/비로그인 두 케이스).
- **Edge cases to cover:** 정의되지 않은 에러 코드로 `fail()` 호출 시 기본값(`INTERNAL_ERROR`/500)
  처리.

**진행 요약:**
- `lib/api/error-codes.ts`: 8개 에러 코드를 `as const` 객체 + 상태 코드 매핑 테이블로 정의,
  `statusForErrorCode()`가 정의되지 않은 코드는 500(INTERNAL_ERROR)으로 폴백.
- `lib/api/response.ts`: `ok(data, message?, status?)` / `fail(code, message, status?)`가
  `NextResponse.json()`으로 ADR-005 엔벨로프 형식을 반환. `fail()`은 status 생략 시 에러 코드의
  매핑된 상태를 자동 사용.
- `lib/domain/auth/require-user.ts`: `requireUser()`가 `{ok:true, userId}` 또는
  `{ok:false, response}` 형태의 discriminated union을 반환 — 호출부에서
  `if (!result.ok) return result.response;` 패턴으로 바로 사용 가능하도록 설계 (1.3의 `auth()`를
  감싸는 얇은 wrapper).
- `app/api/health/route.ts`: 위 유틸 사용 예시. `curl`로 `{"success":true,"data":{"status":"healthy"},"message":"OK"}`
  200 확인.
- 단위 테스트 20건 전부 통과 (response 4건, error-codes 9건, require-user 2건 — 기존 encryption/
  user-service 9건 포함 전체 스위트). `require-user.test.ts`는 `vi.mock("@/lib/auth")`로
  세션 있음/없음 두 케이스를 모킹해 검증.
- `npm run build`/`lint` 통과.

**후속 스토리를 위한 참고:**
- Epic 2~5의 모든 API Route Handler는 `ok()`/`fail()`/`requireUser()`를 그대로 import해서
  재사용한다 — 새 응답 헬퍼를 중복 작성하지 말 것.
- `requireUser()` 사용 패턴: `const r = await requireUser(); if (!r.ok) return r.response; const { userId } = r;`
