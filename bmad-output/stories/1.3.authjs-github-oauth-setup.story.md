# 1.3: Auth.js GitHub OAuth 설정

**Story ID:** 1.3
**Epic:** 1 — Foundation & Project Setup
**Slug:** authjs-github-oauth-setup
**Status:** done
**Branch:** `feature/1.3-authjs-github-oauth-setup` (base: `feature/nextjs-migration`)

> Owned by planning until `ready-for-dev`. Sized to one dev-day (~2-8h). No story points.

## Story

As a **개발자(본인)**,
I want **Auth.js(NextAuth v5)로 GitHub OAuth 로그인·세션·토큰 저장을 구성하**,
so that **이후 모든 인증이 필요한 기능이 안전하고 일관된 세션 메커니즘을 재사용할 수 있다**.

## Acceptance Criteria

1. Auth.js(NextAuth v5)가 GitHub Provider로 설정되어 `app/api/auth/[...nextauth]/route.ts`에서
   로그인/콜백/로그아웃이 동작한다.
2. Auth.js Prisma Adapter가 연결되어 있고, GitHub 로그인 성공 시 `users` 테이블에 사용자가
   upsert된다 (`github_id` 기준, 재로그인 시 중복 생성 없음).
3. GitHub OAuth `access_token`은 `jwt` 콜백에서 획득해 AES-256으로 암호화된 뒤
   `users.github_token`에 저장된다. DB에 평문으로 저장되지 않는다.
4. 세션 전략은 JWT(`session.strategy = "jwt"`)이며, 서버 컴포넌트/Route Handler에서 `auth()`
   헬퍼로 현재 세션(사용자 식별 정보 포함)을 조회할 수 있다.
5. 세션은 만료 전 자동 갱신되도록 `updateAge`가 설정되어 있어, 별도의 커스텀 `/auth/refresh`
   엔드포인트 없이 로그인 상태가 유지된다.

## Dev Notes

- Auth.js GitHub Provider + Prisma Adapter + JWT 세션 전략은 ADR-003의 확정된 결정이다 — 이
  스토리는 그 결정을 실행한다. [Source: architecture.md#adr-003-github-oauth-via-authjs-jwt-세션]
- **중요(LOCKED 결정 실행):** PRD의 FR-002(Access Token 재발급)와 FR-003(로그아웃)은 커스텀
  `/auth/refresh`, `/auth/logout` 엔드포인트가 아니라 Auth.js의 세션 갱신(`updateAge`)과
  `signOut()`으로 대체 구현된다. 이 스토리에서 별도의 refresh/logout Route Handler를 새로 만들지
  않는다. [Source: architecture.md#adr-003-github-oauth-via-authjs-jwt-세션]
- `users.github_token`은 반드시 암호화 저장해야 한다 (NFR-002, LOCKED). 복호화는 서버 사이드에서만
  수행한다. [Source: prd.md#nfr-002-github-access-token-보안--must-security]
- `User` 모델 필드(githubId, username, email, profileImage, githubToken)는 1.2에서 정의된
  스키마를 그대로 사용한다. [Source: architecture.md#5-data-model]
- 인증 필요 API는 이 스토리에서 만든 `auth()` 헬퍼를 기반으로, 1.4에서 만들 인증 가드 유틸이
  감싸서 재사용한다. [Inference]

## Testing

- **Approach:** 도메인 로직(암호화 유틸, User upsert)은 단위 테스트, OAuth 플로우 자체는 실제
  GitHub 계정으로 수동 검증.
- **Key scenarios:** 최초 로그인 시 User 생성, 재로그인 시 기존 User 재사용(row 개수 불변),
  `github_token`이 평문이 아닌 암호문으로 저장됨, 보호된 라우트에서 세션 조회 성공.
- **Per-AC verification:** AC#1 → 브라우저로 GitHub 로그인 플로우 수동 확인(로그인→콜백→세션
  생성); AC#2 → DB에서 동일 `githubId`로 재로그인 시 `users` row 개수가 늘지 않는지 확인; AC#3 →
  DB의 `github_token` 컬럼 값이 원본 GitHub 토큰과 다른(암호화된) 값인지 확인, 암호화 유틸 단위
  테스트로 encrypt→decrypt 왕복 검증; AC#4 → 테스트용 보호 라우트에서 `auth()` 반환값 확인; AC#5 →
  코드 리뷰로 `updateAge` 설정값 확인 (시간 조작 없이 설정 존재 여부로 검증).
- **Fixtures / mocks:** 개발용 GitHub OAuth App(Client ID/Secret), 암호화 유틸 단위 테스트용
  샘플 문자열.
- **Edge cases to cover:** 사용자가 GitHub 로그인 화면에서 거부(cancel)한 경우, GitHub가
  `access_token`을 반환하지 않는 예외 케이스.

## Dev Agent Record

**완료일:** 2026-08-03 (Ralph loop iteration 3)
**Branch:** `feature/1.3-authjs-github-oauth-setup` (base: `feature/nextjs-migration`)

**진행 요약:**
- `next-auth@5.0.0-beta.32` + `@auth/prisma-adapter` 설치. `lib/auth.ts`에 GitHub Provider +
  PrismaAdapter + JWT 세션 전략(`maxAge` 30일, `updateAge` 1일) 구성.
- `@auth/core`의 `handle-login.js` 소스를 직접 확인해 어댑터의 실제 동작을 검증함:
  - `createUser`는 profile()이 반환한 객체에서 `id`를 제거하고 나머지로 `prisma.user.create()`를
    호출한다 — 즉 Prisma가 자체 cuid를 생성하며 GitHub의 숫자 id가 PK로 쓰이지 않는다.
  - OAuth 로그인 시 `emailVerified: null`이 무조건 데이터에 포함되고, `profile.email`이 있으면
    `getUserByEmail(email)`(Prisma `findUnique`)이 호출된다. 이 두 가지 때문에 **schema.prisma에
    원래 없던 `emailVerified` 필드와 `email` 필드의 `@unique` 제약을 추가로 도입해야 했다**
    (안 하면 최초 로그인 시 "Unknown argument emailVerified" 런타임 에러 또는 findUnique 실패로
    깨짐). 이 두 필드/제약은 architecture.md에 명시되진 않았지만 Auth.js PrismaAdapter와의
    호환을 위해 필수임 — 도메인 로직에서는 `emailVerified`를 사용하지 않는다. [Learning]
  - GitHub Provider의 `profile()` 콜백을 커스터마이징해 `{id, githubId, username, email,
    profileImage}`를 반환하도록 해서, 어댑터의 `createUser`가 우리 스키마 필드명(camelCase,
    username/profileImage)에 정확히 매핑되도록 했다 — 기본 매핑(`name`/`image`)을 썼다면
    스키마 불일치로 깨졌을 것.
  - 어댑터가 Account.providerAccountId+provider 기준으로 기존 계정을 찾아 재사용하므로
    (AC#2의 "재로그인 시 중복 생성 없음"), `jwt` 콜백에서는 별도로 User를 다시 upsert하지
    않고 `storeEncryptedGithubToken()`으로 암호화된 access_token만 저장한다.
- `lib/domain/auth/encryption.ts`: AES-256-GCM, 키는 `AUTH_SECRET`을 scrypt로 파생. 랜덤 IV +
  authTag를 ciphertext에 포함.
- `lib/domain/auth/user-service.ts`: `storeEncryptedGithubToken`, `findUserByGithubId`.
- `types/next-auth.d.ts` 추가 — `session.user.id`, `token.userId`, 커스텀 `User` 필드에 대한
  모듈 타입 확장 (Owned File Scope에 없었지만 타입체크 통과에 필수적이라 추가).
- Vitest 도입(`vitest.config.mts`, `npm test` 스크립트) — 이 프로젝트에 테스트 러너가 아직
  없었음. 이후 스토리들도 이 설정을 재사용하면 된다.
- **검증한 것:** `npm run build`/`lint` 통과, Vitest 5개 테스트 통과(암호화 round-trip/변조 감지,
  실제 Neon DB 대상 `storeEncryptedGithubToken`/`findUserByGithubId` CRUD), `npm run dev` 기동 후
  `/api/auth/providers`·`/api/auth/csrf`가 실제 GitHub Provider 설정으로 200 응답.
- **실제 자격증명 필요 — 확인 대기:** 브라우저로 GitHub 로그인 화면을 직접 열어 로그인→콜백→
  세션 생성까지 전체 플로우를 눈으로 확인하는 것(AC#1 최종 검증, AC#2의 실사용자 재로그인 시나리오)은
  헤드리스 환경에서 수행할 수 없어 수동 확인이 필요하다. `npm run dev` 후 `http://localhost:3000`에서
  로그인 버튼(UI는 아직 없음 — Epic 2에서 추가 예정)이나 `http://localhost:3000/api/auth/signin`으로
  직접 확인 가능.

**후속 스토리를 위한 참고:**
- 1.4 이후 인증 가드는 이 스토리의 `auth()` 헬퍼(`lib/auth.ts`)를 그대로 import해서 사용한다.
- Epic 2(로그인/로그아웃 UI)에서 실제 로그인 버튼을 붙이면 그때 전체 브라우저 플로우를 눈으로
  검증할 좋은 기회이니, 그 스토리에서 꼭 한 번 실사용자 로그인 테스트를 해볼 것.
- Prisma 관련 CLI 명령은 여전히 `.env`를 먼저 source해야 하고, `migrate dev`가 비대화형 환경에서
  destructive 변경(unique 제약 추가 등) 경고를 만나면 멈추므로, 그럴 땐 `prisma migrate diff
  --from-config-datasource --to-schema <schema> --script`로 SQL을 직접 뽑아 마이그레이션
  폴더에 저장한 뒤 `prisma migrate deploy`로 적용하는 우회 경로를 사용할 것 (이번 스토리에서
  확립함).
