## Story

As a **사용자(본인)**,
I want **GitHub repo URL(및 선택적 브랜치)로 분석을 요청하**,
so that **수동으로 코드를 훑어보지 않고도 분석이 시작되게 할 수 있다**.

## Acceptance Criteria

1. `POST /api/analysis`는 body `{ repoUrl, branch? }`를 받아 `analysis_jobs` 레코드를 PENDING
   상태로 생성하고 202를 반환한다.
2. 유효하지 않은 GitHub repo URL 형식이면 400 INVALID_REQUEST를 반환하고 Job을 생성하지 않는다.
3. 동일 `repoUrl`에 대해 이미 PENDING/PROCESSING 상태인 Job이 있으면 409 DUPLICATE_REQUEST를
   반환한다.
4. 생성 응답에는 `jobId`, `status`, `repoUrl`, `branch`, `createdAt`이 포함된다.
5. 미인증 요청은 401로 거부된다.

## Dev Notes

- 이 스토리는 Job 생성만 담당한다. 실제 GitHub/AI 처리(파이프라인 실행)는 3.3에서 같은 Route
  Handler 내 `waitUntil()`로 트리거된다. [Source: architecture.md#adr-007-vercel-fluid-compute-기반-비동기-job-처리]
- `branch`를 지정하지 않으면 이 스토리는 값을 그대로(빈 값) 저장하고, 실제 default branch 조회는
  3.2/3.3에서 처리한다. [Source: architecture.md#adr-009-github-커밋pr-수집-범위-제한-및-캐싱]
- 응답 형식은 ADR-005의 JSON 엔벨로프를 따른다(1.4의 `ok()`/`fail()` 재사용).
  [Source: architecture.md#6-api-specifications]
- AnalysisJob 스키마는 1.2에서 정의된 대로 사용한다(repoUrl, repoName, branch, commitSha?,
  status, errorMessage?). [Source: architecture.md#5-data-model]

## Testing

- **Approach:** API 통합 테스트.
- **Key scenarios:** 정상 생성, 잘못된 URL, 중복 요청, 미인증.
- **Per-AC verification:** AC#1 → 통합 테스트로 202 + PENDING 상태 확인; AC#2 → 잘못된 URL 400
  확인; AC#3 → 동일 repoUrl 2회 요청 시 두 번째 요청 409 확인; AC#4 → 응답 필드 존재 확인; AC#5 →
  세션 없이 401 확인.
- **Fixtures / mocks:** 유효/무효 repo URL 샘플 목록.
- **Edge cases to cover:** repoUrl에 `.git` 접미사나 trailing slash가 붙은 변형 형식 처리.
