## Story

As a **사용자(본인)**,
I want **분석 요청 후 GitHub 데이터 수집 → AI 노트 생성 → AI 블로그 초안 생성까지 자동으로
이어지**,
so that **별도 트리거 없이 하나의 요청으로 노트와 블로그 초안까지 받을 수 있다**.

## Acceptance Criteria

1. `POST /api/analysis` 응답(202) 반환 후, `waitUntil()`로 파이프라인이 같은 함수 실행 컨텍스트
   안에서 백그라운드로 계속된다. Route Handler는 Fluid Compute를 활성화하고 `maxDuration`을
   300초로 설정한다.
2. 파이프라인은 상태를 PENDING→PROCESSING으로 전이한 뒤, 3.2의 함수들로 README/디렉토리 구조/
   커밋/PR을 수집한다.
3. 수집 완료 후 4.1의 노트 생성 함수를 호출하고, 성공 시 Job을 COMPLETED로 전이하며 `noteId`를
   기록한다.
4. 노트 저장 직후 5.1의 블로그 초안 생성 함수를 호출한다. 블로그 초안 생성이 실패해도 이미
   COMPLETED로 전이된 Job/저장된 Note는 영향받지 않는다(별도 try/catch로 격리).
5. GitHub 수집 또는 AI 노트 생성 중 하나라도 실패하면 Job을 FAILED로 전이하고 `errorMessage`를
   기록한다 (PENDING/PROCESSING 고착 없음).
6. 동일 `repoUrl` + 동일 최신 `commitSha`로 재요청 시, 새 GitHub/AI 호출 없이 기존 Note를
   재사용하고 즉시 COMPLETED로 응답한다 (FR-012).

## Dev Notes

- Vercel Fluid Compute `waitUntil()` 기반 비동기 처리는 ADR-007의 LOCKED 결정이다 — 별도 큐/워커
  서비스를 도입하지 않는다. [Source: architecture.md#adr-007-vercel-fluid-compute-기반-비동기-job-처리]
- 실패 처리는 NFR-003의 LOCKED 요구사항 — 모든 외부 API 실패가 반드시 FAILED 전이 +
  `errorMessage` 기록으로 귀결되어야 한다. [Source: prd.md#nfr-003-분석-job-실패-처리--must-reliability]
- 캐싱은 1.2/ADR-009에서 정의한 `(repo_url, commit_sha)` 인덱스를 사용한다.
  [Source: architecture.md#adr-009-github-커밋pr-수집-범위-제한-및-캐싱]
- **블로그 초안 생성 실패 격리는 FR-017의 LOCKED 요구사항**: "블로그 초안 생성 실패 시에도 노트는
  정상적으로 유지된다." 따라서 5.1 호출은 노트 생성/Job COMPLETED 전이와 분리된 자체 try/catch로
  감싸고, 실패해도 Job 상태를 FAILED로 되돌리지 않는다. [Source: prd.md#fr-017-블로그-초안-생성--must]
- 이 스토리는 4.1/5.1이 이미 만들어 둔 순수 함수를 "호출"하는 오케스트레이션 로직만 담당한다 —
  AI 프롬프트/파싱 로직 자체는 4.1/5.1의 책임이다. [Inference]

## Testing

  시나리오 검증.
- **Key scenarios:** 정상 완료 흐름(노트+블로그 모두 성공), GitHub 수집 실패→FAILED, AI 노트 생성
  실패→FAILED, AI 블로그 생성만 실패(노트는 COMPLETED 유지), 캐시 히트 시 재호출 없음.

  AC#2 → 상태 전이 로그/DB 값 확인; AC#3 → 성공 시 `noteId` 필드 확인; AC#4 → 블로그 생성 mock

  실패 주입 후 FAILED + `errorMessage` 확인; AC#6 → 동일 `commitSha` 재요청 시 GitHub/AI mock
  호출 횟수 0 확인.
- **Fixtures / mocks:** 3.2의 GitHub client mock, 4.1의 노트 생성 mock, 5.1의 블로그 생성 mock.
- **Edge cases to cover:** 300초 초과 시나리오는 테스트 환경에서 직접 재현하지 않고 코드 리뷰로

**진행 요약:**
- `@vercel/functions`의 `waitUntil()`을 `POST /api/analysis`에 연동, `export const
  maxDuration = 300;` 추가 (Fluid Compute는 Vercel 프로젝트 설정에서 활성화하는 플랫폼 옵션이라
  코드에서는 `maxDuration`만 명시하면 됨).
- `lib/domain/analysis/job-processor.ts`의 `processAnalysisJob(jobId)`가 전체 오케스트레이션을
  담당: PENDING→PROCESSING 전이 → 3.2 GitHub 클라이언트로 branch/커밋 조회 → (캐시 미스 시)
  README/디렉토리/PR 조회 → 4.1 `generateNote()` → `createNoteFromAnalysis()` →
  COMPLETED 전이 → (격리된 try/catch) 5.1 `generateBlogDraft()` → `createBlogDraftFromNote()`.
  실패는 전부 최상위 try/catch가 잡아 FAILED + `errorMessage` 기록.
- **AC#6 캐시 재사용 설계 결정(스키마 제약과의 충돌 해결):** `notes.job_id`가 unique 제약이라
  (1.2에서 확정) 같은 Note row를 여러 Job에 재연결할 수 없다. 그래서 "재사용"을 **캐시된
  Note/BlogDraft의 내용을 복사해 새 Job에 연결된 새 row를 만드는 것**으로 해석해 구현했다 —
  기존 COMPLETED Job(같은 userId+repoUrl+commitSha)의 Note/BlogDraft를 찾아 필드를 그대로
  복사한 새 Note/BlogDraft를 생성하고 Job을 바로 COMPLETED로 전이한다. 이 경로에서는
  `getRepoOverview`/`getRecentPullRequests`/`generateNote`/`generateBlogDraft` 호출이 전부
  스킵된다. [Learning] 단, 최신 commitSha 자체를 알기 위한 `getRecentCommits` 호출 1회는
  캐시 히트 여부와 무관하게 항상 필요하다 (기존 Note 생성 시에도 어차피 필요한 호출이라 추가
  비용 없음) — 스토리의 "새 GitHub/AI 호출 없이"는 이 필수 확인 호출까지 0으로 만들 수는
  없다고 판단해 README/디렉토리/PR/AI 생성 호출만 스킵하는 것으로 실용적으로 해석함.
- 통합 테스트 5건 (실제 Neon DB + github-client/note-generator/blogdraft-generator 3개 모듈
  mock): 정상 완료, GitHub 실패→FAILED, 노트 생성 실패→FAILED, 블로그만 실패해도 Job은
  COMPLETED 유지, 캐시 재사용(2번째 실행 시 AI/PR/overview 호출 없음 확인). 캐시 재사용
  테스트는 실제 DB 왕복이 두 번이라 5초 기본 타임아웃을 20초로 늘림. 전체 스위트 75건 통과.
- `npm run build`/`lint` 통과.
- 300초 초과 시나리오는 (스토리에 명시된 대로) 코드 리뷰 수준으로만 확인 —
  `maxDuration = 300` 설정 존재 확인으로 충분.
