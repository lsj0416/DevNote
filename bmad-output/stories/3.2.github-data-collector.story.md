# 3.2: GitHub 데이터 수집 클라이언트

**Story ID:** 3.2
**Epic:** 3 — Repo 분석 (커밋/PR 포함)
**Slug:** github-data-collector
**Status:** ready-for-dev
**Branch:** `feature/3.2-github-data-collector` (base: `develop`)

> Owned by planning until `ready-for-dev`. Sized to one dev-day (~2-8h). No story points.

## Story

As a **개발자(본인, 파이프라인 구현자 관점)**,
I want **README/디렉토리 구조/커밋/PR을 GitHub API로 수집하는 클라이언트 모듈을 만들**,
so that **분석 Job 파이프라인(3.3)이 이 모듈을 호출해 노트 생성에 필요한 데이터를 얻을 수 있다**.

## Acceptance Criteria

1. `lib/domain/analysis/github-client.ts`에 README와 최상위 디렉토리 구조를 가져오는 함수가
   있다.
2. 지정 브랜치(또는 default branch)의 최신 커밋 최대 50개를 가져오는 함수가 있다.
3. 지정 브랜치 관련 PR 최대 20개(제목/설명/상태)를 가져오는 함수가 있다.
4. README가 없거나 PR이 없는 repo에서도 함수가 예외를 던지지 않고 빈 값/구조로 처리한다.
5. GitHub API 호출 실패(네트워크 오류, 404 등) 시 명확한 에러가 throw되어 호출자가 원인을
   구분할 수 있다.

## Dev Notes

- 커밋 최신 50개 / PR 최근 20개 상한은 ADR-009의 LOCKED 결정이다 — GitHub API 클라이언트는
  반드시 이 상한을 페이지네이션 파라미터로 강제해야 한다.
  [Source: architecture.md#adr-009-github-커밋pr-수집-범위-제한-및-캐싱]
- branch가 지정되지 않으면 GitHub API로 repo의 default branch를 조회해 사용한다.
  [Source: architecture.md#adr-009-github-커밋pr-수집-범위-제한-및-캐싱]
- 이 스토리는 순수 함수/클라이언트 모듈만 만든다. Job 파이프라인 연동(호출 지점)은 3.3에서
  수행한다. [Inference]
- GitHub API 호출은 사용자의 저장된(복호화된) `access_token`을 사용한다 — 1.3에서 만든 암호화
  유틸의 복호화 함수를 재사용한다. [Source: architecture.md#adr-003-github-oauth-via-authjs-jwt-세션]

## Testing

- **Approach:** 단위 테스트(Octokit mock).
- **Key scenarios:** README 있음/없음, 커밋 50개 초과 repo에서 상한 적용, PR 없는 repo, API 실패.
- **Per-AC verification:** AC#1 → mock으로 README 반환 확인; AC#2 → 커밋 50개 초과 fixture로
  상한 적용 확인; AC#3 → PR 20개 초과 fixture로 상한 적용 확인; AC#4 → README/PR 없는 fixture로
  빈 값 처리 확인; AC#5 → mock 404/500 응답 시 특정 에러 타입 throw 확인.
- **Fixtures / mocks:** Octokit mock 응답(README 있음/없음, 커밋 다수, PR 다수/0개, API 에러
  케이스).
- **Edge cases to cover:** private repo 접근 권한 없음(403), GitHub API rate limit 응답
  (403/429).
